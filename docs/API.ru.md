# Справочник API

[English version](API.md)

## Доступ

- `/api/*` обслуживает веб-панель. Защищённые маршруты требуют
  `Authorization: Bearer <operator-session-token>`.
- `/internal/*` обслуживает бота. Передавайте ровно один заголовок
  `X-Internal-Token`. Отсутствующий, повторный или неверный заголовок даёт
  HTTP 401. См. [настройки окружения](ENV_VARS.md).

Базовая конфигурация Compose оставляет порт бэкенда во внутренней сети.
Nginx блокирует внутренние маршруты. Конфигурация разработки публикует
бэкенд на loopback-порту 8080. Используйте Swagger и [k6](OPERATIONS.md#isolated-k6-relay-check)
на изолированном стенде.

## Аутентификация

| Метод | Путь | Результат |
| --- | --- | --- |
| POST | `/api/auth/login` | Успешная проверка пароля возвращает `totp_required` или `totp_setup_required`. |
| POST | `/api/auth/totp/verify` | Проверяет код TOTP и возвращает `session_token`. |
| POST | `/api/auth/logout` | Отзывает текущую сессию. |

За пять минут разрешено пять попыток входа на пару логин и IP и 30 на IP.
Для TOTP разрешено пять проверок на промежуточный токен за срок его действия
и десять на оператора за пять минут. Превышение лимита даёт HTTP 429 с
`Retry-After` в секундах. Недоступность ограничителя даёт HTTP 503.
Неверный пароль, неизвестный логин и неактивная учётная запись дают HTTP 401.
Изменение роли или статуса отзывает сессии и незавершённые входы оператора.

### Вход через OpenID Connect

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | `/api/auth/oidc` | Показывает, включён ли SSO. |
| POST | `/api/auth/oidc/start` | Возвращает `authorization_url` и устанавливает краткоживущий cookie. |
| GET | `/api/auth/oidc/callback` | Проверяет ответ провайдера и перенаправляет в панель. |
| POST | `/api/auth/oidc/complete` | Погашает одноразовый cookie и возвращает `totp_required` и `pending_token`. |

Последние три маршрута доступны при включённом SSO. Используйте единый
HTTPS origin. Неверный, просроченный или использованный cookie даёт HTTP 401.
Завершите вход стандартной проверкой TOTP. См. [настройку SSO](OPERATIONS.md#operator-sso-with-openid-connect).

## Готовность

`GET /api/health` доступен через Nginx. Если PostgreSQL и Redis готовы,
ответ содержит HTTP 200 и `"status": "ok"`. Иначе возвращается HTTP 503
со статусами зависимостей. `GET /health` также доступен напрямую на бэкенде.

```http
GET /api/health HTTP/1.1
Host: panel.example.invalid
```

## Сессии

Администратор видит все сессии. Остальные операторы видят назначенные им сессии.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/sessions` | Список доступных сессий. |
| POST | `/api/sessions` | Создание сессии. |
| GET | `/api/sessions/:id` | Просмотр сессии. |
| POST | `/api/sessions/:id/invites` | Выдача приглашения для `role` (`client` или `executor`). HTTP 201 содержит `token` и `expires_at`. |
| DELETE | `/api/sessions/:id/invites/:role` | Отзыв неиспользованного приглашения. |
| PATCH | `/api/sessions/:id/status` | Изменение статуса. |
| PATCH | `/api/sessions/:id/owner` | Назначение владельца. |
| GET | `/api/sessions/:id/messages` | История сообщений. |
| POST | `/api/sessions/:id/send-as` | Отправка от имени участника активной сессии. |
| GET | `/api/messages/:id/media` | Чтение вложения после проверки доступа к сессии. Поддерживает HTTP Range. |
| GET | `/api/sessions/:id/transcript` | Экспорт истории в CSV или PDF с записью в аудит. |

Приглашение действует 24 часа и используется один раз. Перевыпуск отзывает
предыдущую ссылку для той же роли. Слот должен быть свободен, а сессия
активна. Передавайте ссылку получателю лично. Бот погашает токен через
`POST /internal/sessions/bind`. Уже привязанные участники выбирают сессию
командой `/sessions`.

Для ответа оператора укажите `recipient_role`, ожидаемый
`recipient_user_id` из сессии и ненулевой UUID `request_key` вместе
с `impersonated_role`, `content_type` и `content`. Роль получателя
противоположна роли отправителя. При повторе той же команды используйте
прежний ключ. Ключ действует в пределах учётной записи оператора и
хранится вместе с заданием. Успешный повтор возвращает прежний ID
сообщения. Другой запрос с тем же ключом, смена получателя или
неактивная сессия дают HTTP 409. При отзыве доступа ответ — HTTP 403
или 401 в зависимости от состояния сессии входа.

Ответ с явным получателем содержит `message_id` и `sender_label`.
Запросы без трёх новых полей сохраняют прежние форматы запроса и
ответа. Адресат фиксируется при записи в очередь.

## Операторы и входящие обращения

| Метод | Путь | Доступ |
| --- | --- | --- |
| GET | `/api/operators` | Администратор |
| POST | `/api/operators` | Администратор |
| PATCH | `/api/operators/:id` | Администратор |
| GET | `/api/incoming-requests` | Сессия оператора |
| GET | `/api/incoming-requests/:id` | Сессия оператора. Для назначенного обращения нужен владелец или администратор. |
| POST | `/api/incoming-requests/:id/claim` | Сессия оператора. Назначает новое обращение и возвращает HTTP 204. |
| POST | `/api/incoming-requests/:id/session` | Владелец обращения или администратор. Создаёт или открывает связанную сессию. |
| POST | `/api/incoming-requests/:id/transfer` | Администратор. Передаёт обращение и связанную сессию. |
| PATCH | `/api/incoming-requests/:id/status` | Сессия оператора |

Параметр `status=in_progress` возвращает назначенные вам обращения.
Повторное назначение себе успешно, при конфликте возвращается HTTP 409.
Для создания передайте `title` и при необходимости `language`. API
возвращает HTTP 201 с `id` при создании и HTTP 200 с прежним `id` при
повторе, если у оператора есть доступ к сессии. Назначение, привязка
и соответствующие записи аудита выполняются в транзакциях.
Прежний маршрут изменения статуса отвечает HTTP 409 для назначенных
обращений. Для связанной сессии действуют существующие правила доступа.

Администратор может добавить `scope=all` к `status=in_progress`, чтобы
увидеть все назначенные обращения. Передача принимает `expected_owner_id`
и `operator_id`. Успех и повтор на того же текущего владельца дают HTTP 204.
Если владелец уже изменился, новый оператор неактивен или владельцы карточки
и сессии различаются, API возвращает HTTP 409. Оба назначения и событие
аудита сохраняются в одной транзакции.

Поддерживаются роли `admin` и `operator`. Изменение, после которого не
останется активных администраторов, даёт HTTP 409.

## Журнал аудита

`GET /api/audit-log` доступен администратору. Фильтры включают `actor_id`,
`action`, `target_type`, `date_from` и `date_to`. Даты принимаются
в `YYYY-MM-DD` или RFC 3339. Для `limit` допустимо 1–200, по умолчанию 100.
`offset` по умолчанию равен 0. JSON содержит `actor_type` и `has_more`.
Параметр `format=csv` экспортирует выбранную страницу.

## Доставка сообщений

История содержит `delivered` и `delivery_status`. Возможные статусы новых
сообщений — `queued`, `retrying`, `delivered` и `failed`.
`legacy_unknown` относится к истории до появления очереди. Старое
булево поле само по себе не подтверждает доставку. Сервисные маршруты
привязки и пересылки не возвращают боту Telegram ID получателя или содержимое
ожидающих сообщений. Воркер отправляет их через защищённый маршрут бота.

Сообщение и задание очереди сохраняются в одной транзакции. Задание ожидает
второго участника и выполняется в активной сессии. Повторы после сетевой
ошибки или ошибки Telegram запланированы через 5, 10, 20 и 40 секунд.
Пятая неудача отмечается как `failed`. Отправитель получает личное
уведомление, а для отправки оператором ошибка видна в панели.

Доставка означает подтверждение от API Telegram. Статус прочтения не
проверяется. Воркер резервирует задание на 90 секунд. Повторная доставка
возможна, если подтверждение Telegram потеряно или успех не записан в БД.

Если к моменту взятия задания из очереди получатель сменился, сессия
закрыта или оператор потерял доступ, ответ оператора получает статус
`failed`. Старые задания оператора без сохранённого адресата тоже
завершаются с ошибкой. Пауза откладывает отправку при сохранении
адресата и прав. Уже начатый сетевой вызов нельзя отменить задним числом.

## Экспорт переписки

`GET /api/sessions/:id/transcript?format=csv` или `?format=pdf` выгружает
сохранённую историю по времени. Доступ имеют администратор и назначенный
оператор с Bearer-токеном. Экспорт содержит время UTC, роль отправителя,
тип контента, статус доставки, отметку об отправке оператором, текст и
подписи к медиа. Файлы, их ссылки, идентификаторы участников и название
сессии в выгрузку не входят. Текст участников включён.

CSV использует UTF-8 с BOM и ставит апостроф перед текстом, похожим на
формулу. PDF поддерживает кириллицу и показывает неподдерживаемые
символы в виде `[U+XXXX]`.

Ответ содержит `Cache-Control: no-store`. Для успешной выгрузки нужна
запись `session_transcript_exported` с оператором, сессией, форматом и
числом сообщений. Ошибка записи аудита или занятость всех четырёх слотов
даёт HTTP 503. Лимиты — 2 000 сообщений, 1 МиБ исходного текста и 250
страниц для PDF. Превышение возвращает HTTP 422 без частичного файла.

## Лимиты и пагинация

Лимит тела API — 64 КиБ. При превышении возвращается HTTP 413. Загрузка
медиа через Telegram ограничивается отдельно. Списки сессий, сообщений,
операторов и обращений, а также внутренние списки сессий и обращений
принимают `limit` (1–200, по умолчанию 50) и `offset` и возвращают
`has_more`. Сессии фильтруются по `status` и ищутся по названию или
точному ID через `q`. Страницы истории идут от новых сообщений к старым,
сообщения внутри страницы отсортированы по времени. При равенстве
используется ID. Внутренний список ставит текущую сессию первой.
Telegram-меню запрашивает десять строк на страницу.

Сервисный API повторно использует открытое обращение того же отправителя
или обращение, созданное за последние десять минут. Новое обращение
возвращает HTTP 201 и вызывает оповещение. Повторное возвращает HTTP 200.
В обоих ответах есть `id` и текущий `status` обращения (`new`,
`in_progress` или `processed`). Первый текст без выбранной сессии заполняет пустое поле
первого сообщения.

## Смена и сброс пароля

`POST /api/auth/password` требует сессию оператора, текущий и новый
пароли. Новый пароль содержит не менее 12 символов, занимает до 72 байт
в UTF-8, не содержит управляющих символов и отличается от текущего.
Допускается пять проверок текущего пароля за пять минут на оператора.
HTTP 204 подтверждает смену и отзыв прежних сессий и незавершённых входов.

При временном пароле `POST /api/auth/totp/verify` возвращает
`password_change_required: true` и пятиминутный токен только для смены
пароля и выхода. После смены войдите снова с прежним TOTP.

`POST /api/operators/:id/password/reset` позволяет администратору сбросить
пароль другого активного или приглашённого оператора. Сгенерированный
пароль возвращается один раз с `Cache-Control: no-store`. Сброс требует
смены пароля, отзывает прежние сессии и незавершённые входы, сохраняет
настройку TOTP и отражается в аудите.

## Восстановление TOTP

- `POST /api/auth/totp/recovery-codes` требует полную сессию, текущий пароль
  и код TOTP. Возвращает восемь кодов один раз. В БД хранятся их хеши.
  Перевыпуск отзывает старые коды, сессии и незавершённые входы.
- `POST /api/auth/totp/recover` принимает промежуточный токен после проверки
  пароля и один код восстановления. Токен погашается даже при неверном
  коде. Успех погашает код и выдаёт новую пятиминутную настройку TOTP без
  доступа к панели.
- `POST /api/auth/totp/verify` подтверждает новый аутентификатор, заменяет
  зашифрованный секрет и отзывает прежние сессии, незавершённые входы и
  оставшиеся коды. До подтверждения работает прежний аутентификатор.
  Для перезапуска прерванного восстановления нужен неиспользованный код.

## Привязка Telegram оператора

| Метод | Путь | Доступ | Успех |
| --- | --- | --- | --- |
| GET | `/api/account/telegram-link` | Сессия оператора | 200, `linked` |
| POST | `/api/account/telegram-link` | Сессия оператора | 201, `code` |
| POST | `/internal/operators/telegram-link/claim` | Сервисный токен бота | 200, `confirmation_code` |
| POST | `/api/account/telegram-link/confirm` | Оператор, начавший привязку | 204 |

Бот передаёт `code` и `telegram_id` отправителя в личном чате. Панель
передаёт полученный код подтверждения как `code`. Коды одноразовые и
действуют в рамках исходного пятиминутного срока. Перевыпуск или
изменение версии авторизации закрывает ожидающую привязку. Отсутствующая
или просроченная привязка даёт HTTP 404, конфликт с другим оператором —
HTTP 409. Ответы содержат `Cache-Control: no-store`. Событие
`operator_telegram_linked` хранит внутренний ID оператора.

Сервисный поиск участника возвращает `language_code`, поиск оператора —
`language`. Смена языка принимает `ru` и `en` и применяется к участнику
или привязанному активному оператору. Если оба отсутствуют, ответ HTTP 404.

## События аудита

Аудит охватывает вход с TOTP, выход, отклонённые попытки входа в пределах
лимита, создание сессии, статусы обращений, просмотр медиа, запросы
остановки и переключение сессии ботом. Записи используют внутренние ID
субъектов и объектов. Пароли, токены и TOTP-коды не записываются.
У неизвестного логина нет ID субъекта. Каждый Range-запрос медиа считается
отдельным обращением. Ошибки записи обычного аудита логируются.

При паузе и закрытии сессии связанные участники получают нейтральные
уведомления. Сбой отправки не отменяет сохранённый статус.
